# Stripe lifecycle reconciliation

The signed webhook handles paid checkout/renewal plus `customer.subscription.updated` and `customer.subscription.deleted`. Current provider objects decide the outcome; delivery order and event creation timestamps do not. The raw UTF-8 body is bounded to 1 MiB and verified against the tenant's signing secret before routing. Unsupported signed events, including external refund callbacks in this checkpoint, return 200 without payment writes. Invalid signatures return 400; unavailable configuration or retryable reconciliation returns 503; proven correlation conflicts are retained for review and return 202.

A financial `StripeSubscriptionBinding` pins tenant, test/live mode, provider subscription/customer, native order, user, plan and membership session. It rejects a contradictory existing native owner. Included membership IDs are recorded before their native insert and remain available after a rejoin changes native rows. `StripeWebhookReceipt` deduplicates completed event IDs and records retry/review outcomes without storing webhook bodies, emails or payment-method details.

Only native SUBSCRIPTION plans use subscription-ended access rules. Scheduled cancellation stays active until the provider reports actual `ended_at`. `canceled_at` can be the earlier scheduling request and is never substituted. Paused, past-due and unpaid statuses are recorded for attention; this slice does not invent a grace or pause policy. Existing EMI completion behavior remains separate.

Confirmed ending first caps the binding, then CAS-freezes its existing exact access periods. That second write shares the revision used by drip grants and delivery claims. An already claimed SMTP send cannot be recalled; unclaimed work cannot cross the completed cap. A subscription claim serializes native payment activation and final ending. Late included rows remain read/drip-blocked by their binding even while the claim is occupied. The finishing pass includes historical child periods and never changes a newer native session.

Retention preserves an earlier member-request cutoff and operation. A retrospective end recomputes only when necessary, keeps proved released IDs, and records unknown timing. Native course/lesson write times are context upper bounds, never first-publication dates. A later visibility, assignment or schedule edit cannot prove what was available before an earlier provider cutoff. Existing undated lesson context stays unknown; enabling native Lesson timestamps does not backfill old rows. An in-period edit to old content never manufactures a new drop. Already-frozen snapshots remain stable unless a verified earlier provider end requires a narrower cap. Immediate confirmation also withholds a proven post-cutoff context change.

The complete resolved-member paid callback reserves the account before settling its pending invoice, attaching its subscription and activating access. Closure waits for the reservation, then rechecks financial blockers. A still-present closing account returns a retryable response; an already erased/inactive account can receive financial bookkeeping only and produces a review outcome. No access or personal enrollment data is recreated. Account closure accepts an exact terminal binding as provider-end evidence while retaining its pending checkout and unresolved financial-operation checks.

## Operator verification

Use a configured test tenant and real signed test events. Complete one checkout; verify one paid native invoice, an active exact-session binding and normal library access. Set cancellation at period end and resend an older update: access remains active. Cancel immediately: the binding first caps access, then ends the exact session, retaining only eligible drops. Replay the deletion and delayed renewal: money is recorded once, access does not revive. Rejoin and resend the old deletion: the new session stays active and the old earned IDs remain retained. Inspect the webhook receipt if correlation is unavailable; never repair it by guessing another tenant, session, customer or order.

Configure the local/hosted listener for both subscription event types in addition to the existing checkout/renewal events. Listener and deployment changes belong to the release operator; this source change does not configure or invoke them.

## Recovery and cleanup

Claims deliberately have no automatic expiry. An expired lease alone cannot prove that a paused worker stopped; allowing it to continue alongside a replacement could recreate access. Normal completion/failure releases the exact claim. A stopped-process claim leaves a visible retry receipt; a confirmed end continues to deny unretained reads/drip while reconciliation is pending.

For a truly abandoned claim: stop all tenant webhook/activation workers and forwarding, preserve the binding and receipt in the release evidence, verify the provider's current subscription in the matching mode, and inspect the exact claim ID. Only after proving the old worker cannot resume may the operator conditionally clear that one claim (`domain + mode + subscriptionId + claim.id`), without changing the binding state/cutoff/targets. Restart forwarding and resend the original signed event. Record the operator action with the release evidence. Never clear a claim merely because it is old, reopen an ended state, or manually add retained IDs. An already dispatched message cannot be retracted. Unavailable historic release evidence requires support review, not a backdated publication timestamp.

These two collections retain only financial correlation/audit data, alongside native Invoice/Membership records, through account closure. They are not reassigned to another user or exposed in member DTOs. Tenant removal calls `deleteTenantStripeLifecycle` only after stopping that tenant's provider forwarding and all writers. There is no automatic TTL: late callbacks must not lose their duplicate/session protection.
