# External refund status

The same tenant-signed webhook accepts `refund.created`, `refund.updated`, `refund.failed` and `charge.refunded`. It retrieves the current charge, payment intent, invoice or Checkout session, and complete bounded refund history from the configured provider. Event payload status and delivery time never order money changes. The legacy `charge.refund.updated` event is not used.

`StripeChargeRefunds` is a financial record keyed by tenant, mode and charge. It pins the exact native paid invoice, transaction, membership session and user. A Checkout metadata ID alone cannot assign a charge: the native settled transaction must match the verified Checkout session, or the native renewal transaction must match the provider invoice. Amount, currency, customer, charge, payment intent and mode must agree. Missing paid callbacks can produce a retry until their exact native receipt exists. Ambiguous, multi-charge, transferred, disputed or otherwise unsupported payment shapes require review.

One non-expiring per-charge claim encloses current provider reads and the saved observation. Concurrent callbacks retry rather than replacing an in-flight result. A complete event receipt deduplicates replays; a later distinct event refreshes current provider facts. A crash after observing the provider can leave the claim held. Recovery uses the subscription README's proven-worker-stop procedure with the exact `domain + mode + chargeId + claim.id`; never clear a claim because of its age. Resending a webhook cannot create another refund because this adapter has no provider-create call.

The native invoice stays paid at its original amount. Its receipt shows the original settlement plus a separate refund summary: each exact pending, requires-action, succeeded, failed or canceled status; succeeded total; and observation time. DTO amounts use major currency units. Provider IDs, metadata and payment methods remain private. A failed/canceled refund is not presented as money returned. Summary absence means unrecorded, not zero refunds.

A native cancellation/refund operation with an already-recorded exact refund ID can show the fresh observed status if charge, user, membership session, mode, amount and currency match. This is a read projection only: it does not claim, approve, decline or complete the operation, create member consent, cancel subscriptions, alter enrollment or apply an access decision. Submitted requests retain their own approval history. Separately, the signed/current full cumulative one-time refund now applies Al’s approved session-scoped access rule without an additional ad hoc decision. Partial refunds keep access; monthly subscription access remains governed by cancellation. Pending access work has its existing reconciliation action. Ambiguous class roster/tag ownership is explicitly flagged, preserving another possible valid grant. A later bank return marks access recovery for review rather than recreating enrollment.

Freshness is causal, not a terminal-status ranking or an event timestamp comparison. Before and after its provider reads, the webhook captures the matching native operation identities, revisions and money observations. A native claim (including an expired claim) or any intervening revision change forces retry. Native money results receive a new observation token only when the provider result is saved. A subsequent exact native token supersedes an older webhook status in operation, receipt, billing and closure reads; an unrelated explanation/access revision does not. Unchanged native money observations may use newer webhook evidence, including a succeeded refund later returning as failed or requiring action. Older ledgers without captured baselines cannot override native results; a distinct signed event or reviewed stopped-worker recovery refreshes them. The original ledger remains unchanged by these read projections.

Account closure blocks while a known ledger is bound, claimed, pending or requires action. Existing submitted requests, pending access/cancellation, checkout and other financial blockers remain. Financial records can continue to reconcile after personal account erasure; no user, access period or subscription membership is recreated.

The ledger is retained through account closure with invoices and subscription bindings. Tenant deletion removes it through `deleteTenantStripeLifecycle` only after provider forwarding and all writers stop. It has no TTL. This feature configures no Stripe receipt-email preference and sends no mail.

The global and product Transactions lists return explicit removal eligibility and a reason. Provider receipts, including failed/pending/test payments, subscription bindings and refund/cancellation records prevent destructive test cleanup. Only explicitly synthetic test rows without those records and still on the same membership session remain removable. Both lists use the same visible reason in place of the removal control, and the mutation rechecks. Community deletion checks the same financial evidence before deleting any community data or calling a provider. This protects correlation needed by delayed callbacks and preserves receipts through account closure. Member labels in both Transactions lists use the shared, permission-gated Member Mimic entry; erased/missing users have no link.

For verification in an authorized test tenant: refund part of a settled charge; replay and reorder the signed refund events; confirm the original receipt remains and each status updates independently. Complete the remaining one-time purchase refund and verify only its correlated access ends, with original money records unchanged. Repeat for an old renewal after rejoining and verify only the original receipt's refund summary changes. A pending refund should block account closure; an unapproved request should retain its decision history even when independently verified full money evidence ends the correlated grant. Use the exact operation reconciliation control for approved access work. Add all four event types to the release operator's listener configuration.

For Transactions verification, open the global list and a product list containing a provider test receipt. Both show why it is kept and offer no removal control. A member link enters the shared read-only profile and Exit returns to the originating list; a course-only operator without user management sees plain text. A permitted synthetic row still opens the existing explicit removal confirmation. A crafted delete request for a provider receipt or an older membership session must fail without losing its invoice or membership.
