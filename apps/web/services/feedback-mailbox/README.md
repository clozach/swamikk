# Private feedback mailbox

X01 creates one private feedback record with notification intent in the same Mongo insert. API success means the feedback is saved; it does not depend on SMTP or queue availability. Visitors/members remain text-only. Admin photo IDs resolve through the existing authenticated feedback-photo route; email includes no photo URL or attachment. No model provider or AI reader is connected by this change.

In **Changes → Private mailbox**, an administrator with `setting:manage` can enable delivery to the existing owner address or another explicitly approved operational recipient and set an interval of 1–10,080 minutes. Delivery starts off. The server records the approving admin and time in existing `Domain.settings.feedbackMailbox`, excluded from public site information. Enabling also releases open feedback already waiting. Existing older feedback without notification intent stays unqueued until an admin chooses **Queue notification again**.

New comments become eligible at the next configured interval boundary. The existing queue service polls once a minute and handles at most 25 due messages per domain per scan. It uses the queue's existing `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_USER`, `EMAIL_PASS`, `EMAIL_FROM`, `DOMAIN`, `PROTOCOL` and `MULTITENANT` settings. SMTP sending runs only with `NODE_ENV=production`, including the local production-mode Mailpit rehearsal. Missing configuration produces a visible definite failure, never a console “sent” fallback. Operator settings do not choose or purchase a provider.

The queue builds the authenticated review URL from the configured site domain, never a visitor-supplied host/target. It sends one recipient a short, HTML-escaped excerpt identified as untrusted quoted data, the role/context and a review link. The email neither executes requests nor approves changes. Delivery logs contain a tenant ID and fixed failure message, not feedback, recipients or credentials.

| Notification state | Meaning and recovery                                                                                                                                                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pending            | Durable intent; eligible time is visible. Delivery off or a stopped queue leaves it saved.                                                                                                                                                           |
| Sending            | An atomic claim prevents another worker from sending the same intent.                                                                                                                                                                                |
| Accepted           | SMTP explicitly accepted the message, or an operator confirmed receipt. This is not proof of inbox delivery or reading. No resend action is offered.                                                                                                 |
| Failed             | Known non-acceptance. Explicit temporary SMTP rejection/DNS failure retries with 1, 2, 4, 8 minute backoff, up to five total attempts. Permanent/configuration failures wait for an admin to fix the cause and queue again.                          |
| Uncertain          | SMTP disconnect/timeout, unexpected adapter failure or an expired three-minute claim. No automatic retry. Check the message reference in the mailbox/provider logs, then explicitly confirm receipt or confirm it was not sent before queuing again. |

A mail server can accept a message just before the connection drops, or before the database becomes unavailable. The code therefore does not promise exactly-once external delivery. Even `ECONNECTION`/`ETIMEDOUT` with command `CONN` is uncertain: the installed Nodemailer connection-close/socket-timeout paths use that label after submission too. A stable per-attempt Message-ID assists investigation; it is not a deduplication guarantee. See [Nodemailer SMTP options](https://nodemailer.com/smtp) and the installed `smtp-connection` implementation. Definite known acceptance is never automatically resent. If persistence fails after acceptance, the lease becomes uncertain and requires reconciliation.

Handling and delivery remain separate. Closing a pending comment prevents dispatch; reopening preserves its original delivery state. Reopening accepted feedback does not send again. A message already in progress cannot be retracted by closing/deleting feedback; the worker records its result without reopening the comment. An admin recipient change/disable is checked again immediately before transport. Reconciliation compares the exact latest feedback timestamp and stores the actual admin's action, rejecting stale requests.

API fragment: `apps/web/app/api/feedback-mailbox/openapi.mjs` exports its default object for the central OpenAPI assembler. All writes require same-origin JSON and the existing session; tenant/permissions come from server context. Member Mimic's write guard remains authoritative. These operations never apply content changes.

## Local rollout verification (root owns runtime)

1. Rebuild common-models, ORM, common-logic, web and queue, then use the existing isolated SMTP/Mailpit rig. No external send was performed while implementing this change.
2. Open Changes as the settings administrator. Verify **Delivery off**, the existing owner recipient and explicit private-recipient approval. Enable with a one-minute interval.
3. Submit public/member text feedback. Confirm the API returns saved feedback before a message is sent; public output must not contain notification recipient/status metadata. An admin-only photo remains behind sign-in and absent from email URLs.
4. After the queue interval, inspect the Mailpit message and follow its review link while signed in. It focuses the correct feedback card. Verify **Accepted by the mail server** and its limited meaning.
5. Stop/restart the queue around pending intent. Simulate a definite SMTP rejection and a disconnected uncertain outcome using isolated test doubles; never deliberately duplicate a real message. Verify backoff/limit and explicit uncertain reconciliation.
6. Close/reopen pending and accepted comments; accepted comments must not resend. Test a member, cross-tenant account, stale reconciliation and cross-origin settings request. Reset any demo settings and synthetic records deliberately after the review.

Automated tests cover atomic saving/private projection, cadence, concurrent claims, definite retries and limits, failed acceptance persistence, expired claims, uncertain reconciliation, tenancy, roles, close/reopen, sender escaping/no photo URL, SMTP classification and accessible approval controls. Actual SMTP arrival and the running page still require the local rollout checks above.
