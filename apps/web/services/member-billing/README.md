# Member billing and monthly cancellation

The browser contract is `types.ts`; the route is `/api/member-billing`. Import the types without importing server services. The OpenAPI fragment lives beside the route and must be registered by the app's API index.

GET reads the current authenticated member's tenant-scoped parent memberships, native settled invoices including that membership's historical checkout sessions, an existing cancellation and a consequence preview. It never contacts Stripe, initializes access or freezes retention. Member Mimic resolves the real administrator's approved subject and returns `readOnly: true`; expired Mimic refuses the read. Provider identifiers and credentials never appear in this projection. Native invoice amounts are major currency units; refund quotes use Stripe minor units. Existing invoices lack a dedicated settlement timestamp or safe read-only receipt page, so `paidAt` is null and receipt links are unavailable.

POST requires a real member, same-origin JSON and no Mimic cookie/context. The three strict commands accept a local membership ID for `prepare`, or an operation ID plus exact quote hash for `confirm` and `reconcile`. Browser-supplied provider IDs and extra fields are rejected. Supporting someone else's billing remains a separate administrative workflow.

Prepare verifies the current tenant/member/session and stored plan, obtains the native Stripe quote, and persists a unique `BillingCancellation` record for that membership session. Provider mode comes from the stored tenant Stripe key and is checked against native settled invoices and the retrieved provider objects; it never defaults to live mode. The quote expires after ten minutes or at the native period boundary, whichever comes first. No access freeze or refund occurs during prepare. Legacy or missing access timing, annual/EMI/complex plans, or unsupported providers return a clear review requirement. Preparation never invents activation or release dates.

Confirm rechecks the exact quote, current membership session/subscription, included membership set and known access timing. If provenance becomes unknown before confirmation, it stops before a claim or access freeze. If it becomes unknown during the freeze, the prepared snapshot remains capped for review and Stripe is not called. Known retained counts can naturally increase while the quote is open. A Mongo compare-and-set claim fixes the cancellation cutoff before `prepareRetention` runs for every involved course. Parent and included course memberships are identified by tenant, member, parent payment plan and exact session. Cancellation is then immediate with no proration/final invoice. Provider-confirmed cancellation is persisted before ending access and mirroring native membership status to `EXPIRED`. Those native updates use the original membership/session and cannot expire a newly started checkout. Existing access and billing records are retained.

The five-minute processing lease excludes simultaneous workers. A crash retains the cancellation/refund intent; explicit reconciliation can recover after the lease expires. Retention operations reuse the exact operation and cutoff. A partially failed access/native-status mirror is idempotently finished before refund work. Cancellation remains separate from refund state: pending, failed, uncertain or review-required refunds do not restore canceled access. The closing gift is available once access is ended and links to `/dashboard/my-content`.

The first refund attempt has its own durable compare-and-set claim. Only the worker receiving that claim may pass `allowCreate: true` to the Stripe adapter. A lost database response after the claim, provider timeout, or process crash is reconciled with `false`; lack of provider metadata is not proof that creating another refund is safe. Native terminal refund results are preserved. Failed/canceled refunds or definite provider rejection require reviewed recovery, not an automatic second operation. A matching pending/requires-action refund can be checked again.

An unconfirmed or ambiguous cancellation remains capped. This self-service service does not call `abortRetention`: reopening requires separate, explicit proof that cancellation failed and the correct provider subscription remains active. An active-provider read alone after a timeout is insufficient. The service changes no global marketing/newsletter preferences and sends no email.

Tests run against an isolated Mongo database and injected Stripe fixtures. They cover concurrent preparation/confirmation, stale sessions and period expiry, parent/included retention, provider and database uncertainty, accepted-refund recovery, exact provider mode, ownership, Mimic and same-origin boundaries. No runtime data or actual provider account is used by these tests.
