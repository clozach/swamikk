# Account closure

M05 `/dashboard/profile#account-closure` opens a consequence review. GET `/api/account-closure` uses Better Auth's persisted session (`disableCookieCache: true`); DELETE requires that real sign-in to be at most ten minutes old, the current review hash and typed `CLOSE`. Older sessions use normal sign-out/sign-in, not a checkbox claiming reauthentication. Mimic has no controls and all closure routes reject its cookie directly. Session/user identity must match in the current tenant. A stale authenticated session is not downgraded to anonymous feedback.

Closure refuses unconfirmed provider subscription references, pending native checkout invoices, unsettled cancellation/refund actions and the site-owner account. A community creator membership with invoice history also needs a reviewed handover, so native ownership migration cannot transfer or remove its receipt identity. Resolve these through Membership or Contact before erasure. It does not cancel or refund a provider operation. Checkout persists its native pending invoice/session before asking the provider; a timeout retains that evidence and blocks account erasure. Signed webhook handling is a separately coordinated lifecycle gate; preserve provider recovery and do not fabricate an outcome.

`packages/common-logic/src/account-lifecycle` stores a tenant/user fence. Writers reserve the account while active, then release in `finally`. Closing atomically refuses new reservations and reports existing ones. Cleanup begins only at zero reservations. The states are active → closing → erasing → erased; only closing can return to active. A crash leaves a named reservation without TTL. Do not remove one because time elapsed: identify the worker, establish that it stopped, reconcile any external attempt, then remove the specific reservation under reviewed operator control. There is no automatic stuck-worker override in this MVP. Erasure failures retain an inactive account/fence for support to resume; the UI does not claim completion on an error.

The fence covers native authenticated GraphQL executions (queries can record activity), explicit target user IDs/email/membership references as well as the real actor, feedback creation, refund drafts/review, member billing, checkout, email tracking, access and O11 creators, in-app notifications and sequence delivery. A sole `deleteUser` mutation uses its dedicated actor/target closure flow; mixing deletion with other GraphQL fields is refused. No nested reservation waits for another reservation, so nesting does not create a lock deadlock. Root/owners coordinate webhook adoption separately.

Private contact choices/photo bytes, feedback, unsubmitted refund drafts, learner activity, notification preferences, recipient email events/delivery history and queued sequence rows are removed; discussions are redacted as in the native cleanup. Recipient mail history and queued sequences are not reassigned to the successor. Native business ownership can transfer to the successor. Invoices and expired Membership references remain for receipts and reconciliation. Submitted/decided/attempted refund records and active content/release operation locks are retained. A refund operator can reconcile a retained existing attempt for an erased account, but cannot initiate a new one. The erased lifecycle and contact tombstones retain only bounded identifiers/state/revision/time needed to reject late writes.

All linked tenant authentication accounts and sessions are removed. The current profile unmounts its private children and clears profile context after successful closure. Only that account's COMMENTS/page-edit sessionStorage keys are cleared; other accounts' drafts are untouched. Browser histories/copies, database backups, old completed Redis job payload history and emails already accepted by SMTP are not represented as erased. New notification jobs contain identifiers and re-read current records before emission; deployment/legacy queue-retention cleanup belongs to the runtime owner. No source test sends external email or calls a payment provider.

New enrollment, lead-download and activity MAIL jobs carry stable tenant/account identity and reserve those accounts through enqueue/fallback and worker SMTP. Drip jobs derive identity from their exact ledger period and hold the reservation through claim, SMTP and result. Private feedback notification delivery similarly reserves its member/admin author through the delivery result. OTP/auth mail, anonymous feedback and historical ordinary MAIL jobs without account provenance remain separate; no email-to-user mapping is invented after erasure. Old queue history, operational delivery logs and accepted mail are not erased. Account review still states that previously queued/sent messages may arrive. See queue `src/domain/account-mail.md` for the tested boundaries and runtime handoff.

## Verification and release

Server tests: `app/api/account-closure/__tests__` reproduce delayed Feedback/refund/native discussion, tracking, checkout and private-data cleanup boundaries using isolated Mongo. Existing admin deletion tests retain invoice references and refuse real provider cancellation. Client tests verify review, recent identity, blockers, Mimic, saved-account reopening and success despite a later sign-out failure. Queue sequence tests pause mocked SMTP and prove erasure waits through its receipt write; accepted mail cannot be recalled. Adjacent queue rendering tests require `NODE_OPTIONS=--experimental-vm-modules`.

Root registers `accountClosureApiOpenApi`, builds/deploys, and provides the M05/O02 visual Changes evidence. O02's existing admin deletion now fails before side effects when closure needs review; it uses the actual admin as successor and retains financial relationships. No native page data mutation is required. Source rollback is the integration commit; do not delete persisted fences or undo erased account data as a code rollback. Tenant teardown can physically remove lifecycle rows only after all tenant ingress/workers stop, following the existing tenant cleanup contract.
