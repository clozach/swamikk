# Member edits

Editing a member's record from Member Mimic. An admin with `user:manage` viewing a member through Mimic may change the member's **name**, **sign-in email**, **preferred contact** (kind and value) and **check-ins**. Every request carries the `courselit.member-mimic` cookie; `requireMimicEditor` re-verifies it through `resolveMemberReadContext`, takes the **editor from `actor`** (the real admin) and the **subject from `memberMimic.subjectUserId`** (loaded fresh from the users collection, never the read-only projection). No cookie → 403 `forbidden`; an expired view → 403 `mimic_expired`. Rate limits key on the admin.

## Routes

- `GET /api/member-edits` → `{ snapshot }` — `MemberEditSnapshot`: subject `{userId, name, email}`, contact `{kind, value, checkIns, revision}` (revision 0 with the sign-in email as the default when nothing is stored), `emailLock` (`self` | `owner`) when the email cannot be changed, `actor {userId, name, canReviewRefunds}`, `pendingEmail` when an email change awaits its code. 60/min.
- `POST /api/member-edits` — `MemberEditInput` `{ changes[1..3] {field, before, after}, undoOf? }` → `MemberEditResult`. `name` and `email` each travel alone; contact kind/value and check-ins may travel together. Fields are unique; new `after` values are trimmed (email lower-cased). A history restoration preserves the stored bytes. Every `before` is compared with the stored value **before any write**; a mismatch is 409 `{ error: {code: "stale", message}, current: [{field, value}] }`. Nothing different → 400 `no_change`. The resulting record must be whole: a non-blank new name, and a contact kind/value pair that passes the member's own preferences rules. An existing blank name can be restored from history. `undoOf` must name an applied row of this member (else 404), and the posted fields and `after` values must match that row's recorded `before` values. 60/min.
- `GET /api/member-edits/history?before=` → `MemberEditHistory` — applied rows newest first, 50 per page, tie-broken cursor `{at, editId}`; each row's `editor {userId, name, email}` resolved from the users collection at read time. 60/min.
- `POST /api/member-edits/email` — `MemberEmailInput` (`confirm {pendingId, code}` | `resend {pendingId}` | `cancel {pendingId}`) → `MemberEmailResult`. 6/min.

The proxy's Mimic allow-list admits exactly these paths (GET/HEAD + POST on `/api/member-edits`, GET/HEAD on `/history`, POST on `/email`).

## Rows

`MemberEdit` (collection `memberedits`; schema in `packages/orm-models/src/models/member-edit.ts`): `editId`, `subjectUserId`, `editorUserId`, `mimicId`, `at`, `changes[{field, before, after}]`, `undoOf`, `emailVerification`, `state` (`pending` → `applying` → `applied` | `failed`), `failureReason`; a pending email row also carries `codeHash`, `codeSalt`, `attempts`, `resends`, `expiresAt` — never returned. Unique `{domain, editId}`; `{domain, subjectUserId, state, at}` for listing; `{domain, subjectUserId, state, expiresAt}` for the pending lookup; **no TTL**. Original editor, subject, time and before/after values remain unchanged. Lifecycle transitions compare the previous state. Email effects have their own `pending` → `complete` status; `complete` means member sessions were revoked and the old-address notice was accepted by the mail service. A partial unique index allows at most one pending email row per member and editor.

## Write protocol

Each request writes one record family. The history row is created `applying` inside the subject and actor account-lifecycle reservations, **before** the record write. Name/email changes write User; contact/check-ins write ContactPreferences. The record CAS writes the changed values and adds the edit ID to its private `memberEditReceipts` array in the **same atomic operation**. User writes compare the stored field value and leave _Last active_ unchanged; contact writes compare the preference revision and upsert only at revision 0. A proven CAS miss marks the attempt failed; an ambiguous database error leaves its applying row intact.

History is settled applied before its source receipt is removed. A snapshot, History read or next edit recovers outstanding receipts first, proving which writes landed even if the response was lost, the process exited, or another writer since changed the value again. Every recovered row retains the initiating admin's ID. Receipts never appear in ordinary member queries or API responses. A failure before the record CAS leaves an attempted row but no false applied history; an edit spanning User and ContactPreferences is rejected before either write.

## Email

The address is normalised (`sanitizeEmail`). Refused: the admin's own account, the site owner's account (403), an address any other account in the tenant holds (409 `conflict`). An address the account held before — the current one or the `before` of an applied email row — applies at once with `emailVerification: previously-held`. A never-held address gets a `pending` row (six-digit code from `crypto.randomInt`, sha256(salt + code), ten minutes, five attempts, three resends; a newer proposal supersedes the older pending) and the code is mailed to the new address with the same pug `MagicCodeEmailTemplate` sign-in uses. Code attempts, expiry, resends and confirmation compare the observed code generation and state. A late wrong code cannot erase a successful confirmation, and a resend invalidates a concurrent old-code claim. On confirm the email lands with `emailVerified: true` (Better Auth's field; `strict: false`), the member's sessions are deleted with the statement account erasure uses, and the old address gets a plain notice naming the change. The receipt remains until both effects finish. Applied responses and history expose `emailEffects: pending | complete`; snapshots expose `emailEffects: pending` when a notice still awaits retry. A session-revocation error returns the shared 503 response with history and receipt retained; a notification error returns the applied record with pending status. The next Mimic edit-panel read retries either. Delivery is at least once: an interrupted enqueue acknowledgment can cause a duplicate notice, carrying the same deterministic Message-ID. No notice-success claim is made before the mail service accepts it. Neither mail is bound to an account (`addMailJob`'s `account` fence admits only the account's _current_ address, which neither recipient is).

## Erasure

`purgeMemberEdits(domain, userId)` deletes every row where the member is the subject; `cleanupPersonalData` calls it beside the contact-preferences tombstone. `deleteTenantMemberEdits(domain)` is the tenant-removal helper.
