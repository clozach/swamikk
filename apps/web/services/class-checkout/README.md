# Dated class checkout — P04 / M07 / O06 / O10

The existing cohort detail form can opt a private roster into `listed-closed` or `listed-open`. Legacy cohorts remain private. Opening requires a bounded name, a real future start, a published course and an active paid one-time plan. A listed class can close or reopen; it cannot revert to an internal roster or be individually deleted. Only name, UTC start and an opaque choice fingerprint become public. Cohort GraphQL reads and rosters keep their existing administration permission.

`GET /api/class-checkout?courseId=…&planId=…` is anonymous, bounded and no-store. It returns `ordinary` or up to 100 explicitly listed class choices. An all-closed list remains a class offer with no available dates; it cannot become an undated purchase. `GET /api/class-checkout/status?courseId=…` is current-owner-only and refuses Mimic. It returns only an order/reference, safe status and, for a reusable checkout, the chosen plan and opaque choice. It does not expose another account, roster, provider identifier or checkout URL.

The existing checkout adds a named date selector, UTC date/time, and contact help. Selection survives sign-in in this tab and is revalidated against the current fingerprint. The payment request accepts only `classChoice: {cohortId, fingerprint}`; dates, owner IDs and provenance come from the server. A one-time plan on a course with listed cohorts requires that choice even when a crafted request omits it. Other plan types retain their native payment path. Already-active course owners see contact help before payment: repeat purchases of the same course/multiple concurrent class orders are **not implemented**.

## Allocation and payment evidence

The entire initiation runs under the existing account write reservation. Every course plan also holds the same tenant/user/course `CheckoutReservation`, preventing a concurrent subscription checkout from replacing a class checkout's sole membership session. Course guards are released in `finally`; they have no expiry that could authorize another worker while the first is finishing.

`ClassCheckoutIntent` is a retained financial record. Its `allocating → creating → ready → completed` path owns one native invoice, membership/session and frozen booking. `allocation-failed` means preparation failed before a provider attempt was accepted and cleanup still needs review. Only a compare-and-swap from `allocating`, followed by retiring an unattempted pending invoice with no provider/settlement fields (or proving no invoice exists), reaches `not-started`; that retained audit permits a new reviewed attempt. `uncertain` retains the provider first-attempt time when acknowledgement may have been lost and cannot authorize another provider creation. An unresolved class intent blocks other plan initiation for the same member/course. All native invoice and `RefundBookingEvidence.source=checkout` fields, including the cohort document ID, choice fingerprint and booked start, persist before `creating` permits the provider call.

The current class adapter supports the existing Stripe connection. It does not change native promotion codes: the confirmed paid amount may be discounted. It does not add a provider idempotency key or retry an unknown provider call. A retry returns the same saved Checkout URL only when plan, selected fingerprint and current membership session still match. Changed dates/listings after allocation require review; an already-issued provider checkout may still be paid for its frozen booked date. Do not claim that closing the listing recalls that provider checkout.

The existing paid-activation follow-up requires the same active native membership/session, tenant invoice, Stripe settlement provenance, amount/currency and booking intent. It rechecks the frozen fingerprint and uses the reviewed revision/name/date in the roster write, adds only the selected cohort and mirror tag idempotently, then records completion. Duplicate completed callbacks do not restore a manually removed roster entry. Listing changes do not rewrite the booked date. Native activation marks the product membership active before this follow-up; a changed date/listing can therefore leave paid product membership active while the class roster needs review. Both the checkout and native payment-return page disclose `paid-review`, the frozen selected date/reference, the actual membership state and contact help. This does not promise a class place or bypass the normal lesson/access ledger. Refund evidence reads require this completed association and the matching current cohort date; otherwise they report unknown for human review. Existing operator verification and historical receipts remain supported; no legacy dates are inferred. The purchase/class refund access decision remains `policy-pending`, so this addition does not enable automatic financial refunds.

Course-wide roster synchronization refuses listed classes, including a listing change before its roster write. It retains existing private-roster behavior. Manual administrator roster management remains available and does not manufacture paid booking evidence.

## Operational recovery

The member receives the durable order/reference and `/p/contact`, never a suggestion to pay again while an attempt is unknown. `/checkout/verify?id=<native invoice ID>` reads the owned native invoice; it does **not** retrieve or reconcile Stripe. Receipt viewing also does not create evidence. Known paid provider sessions recover through the original authenticated callback with the original tenant/invoice/session metadata; a missing or unknown session requires human provider inspection first. An undiscovered or unpaid attempt cannot be fixed by inventing or replaying a payment event.

For a stopped-worker reservation, use the reference to locate precisely one `CheckoutReservation` by tenant/user/course and `state.id` (or its native `state.invoiceId`), the matching account-lifecycle write, native invoice, class intent and booking evidence. Preserve their preimages and provider evidence in the restricted operator incident record. Establish that the original app/worker process is stopped and cannot resume; elapsed time is insufficient. Reconcile any provider attempt and pending financial evidence before allowing another payment. Do not remove a guard while that process or a callback is finishing.

After that review, an operator can compare-and-swap **only the observed guard** using tenant/user/course plus the observed `state.kind=held`, `state.id`, `state.startedAt` and `state.invoiceId` (including absence), setting it to `idle`. A changed or absent record is a refusal, not permission to retry broadly. Remove only the specifically proved stopped account reservation under the existing account-lifecycle recovery procedure. Releasing the course guard alone does not clear a class intent or pending invoice and does not authorize a second payment. There is no public/admin force-unlock endpoint, timer release, automatic abandonment of an accepted/unknown provider attempt, or generic provider recovery tool in this MVP. The sole automatic retirement applies to the proved pre-provider `allocating` state described above. Unresolved financial records remain with human support until their actual outcome is established; preserve them rather than resetting first-attempt evidence.

Account erasure cleanup shares `requireAccountErasureReady`, removes only idle course reservations, and retains class intent/booking financial history under the existing financial-audit policy. A closing/erased account cannot allocate a late reservation or join a roster through paid activation. Already-sent provider communications and existing database backups are outside this source change.

## Verification and release

Isolated tests live in `app/api/class-checkout/__tests__`: native GraphQL listing/revision/permission, public privacy, stale selection, duplicate/cross-plan provider races, exact booking before provider, timeout retention, discounted/duplicate/invalid paid callbacks and closure during allocation. Client tests cover accessible selection, sign-in preservation, changed choice invalidation, closed/error states and pending help across plans. Run these with the existing web server/client Jest configurations; native payment/cohort/refund/account-closure suites are adjacent gates.

Source does not open any cohort, initiate a payment, send an email, deploy a route or answer the refund-access policy decision. Root owns central OpenAPI registration and native/browser evidence. Manual acceptance: explicitly list a synthetic future class, choose its date on the existing checkout, inspect the dated order before a test payment, then verify only that cohort's roster and its retained booking evidence. Rehearse active-owner help, all-closed choices and uncertain-order contact without another provider attempt.
