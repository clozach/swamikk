# Account-bound mail

New enrollment, lead-download and activity-notice jobs carry stable recipient IDs and, where applicable, the real actor ID. Web signs the tenant and recipient in its existing service token; `/job/mail` takes the tenant from that verified token and refuses a mismatched recipient. The current tenant/user/email must still match before enqueue and SMTP. An address is never used to find a replacement account after erasure, and changed addresses do not redirect old mail.

`withAccountMail` reserves the recipient and optional actor while enqueue or web fallback SMTP runs. The mail worker checks again and holds its reservation through SMTP. A closing, erased, inactive, foreign or mismatched account is an acknowledged skip. HTTP account refusals never trigger local fallback. New account-bound queue payloads are removed after completion/failure; queued copies remain until workers finalize them. Existing queue-unavailable fallback behavior remains: an ambiguous enqueue response is not proof the first enqueue failed, so this change does not claim exactly-once SMTP.

Drip jobs already carry an exact tenant/period/delivery identity. This includes old drip jobs: the worker derives their user from that ledger period and holds an account reservation around the existing claim → SMTP → sent/uncertain result. A missing period is skipped. Cancellation still contends on the existing delivery ledger; an SMTP attempt already in flight cannot be recalled. No access scheduling, cancellation policy or provider logic changed.

Lead downloads and admin invitations hold the resolved recipient from membership creation through the download-link/mail operation, including a newly created invitee that was absent from the Graph ingress snapshot. Private feedback notification delivery holds a member/admin author's account through the current-row check, SMTP and outcome write. A closure refusal before transport records non-retryable rejection on an existing feedback row only; it cannot recreate an erased row. Visitor feedback has no account identity and remains independent.

A free download request does not grant newsletter consent. New download recipients start with updates off; existing preferences remain unchanged and the dedicated newsletter form still opts in/resubscribes. The creator sweep found the shared `createUser` default, authentication creation, admin enrollment and site-owner initialization already default to false. API creation accepts an explicit caller-supplied boolean; newsletter signup deliberately calls the consent service. Queue audience filters and Mimic field allowlists are reads, not opt-in creators.

OTP/auth mail and historical ordinary MAIL jobs have no persisted account provenance. Their existing behavior remains explicit, with no inferred email-to-user mapping. This does not erase old queue history, operational mail logs, external mailbox copies or accepted SMTP. New identifiable jobs drain through the gate after deployment; old provenance-less jobs need a separate, reviewed runtime disposition. Crashed reservations retain the existing account-closure recovery rule: no time-based deletion of a possibly active side-effect claim.

Roll out the queue support before the web producer changes, or stop producers during a coordinated rollout. An older worker cannot enforce provenance it does not understand. This source lane performs no deployment, queue purge or external send.

Isolated Mongo/mock tests cover post-closure recipient/actor skips, same-email replacement refusal, exact tenant/email matching, enqueue/fallback and SMTP barriers, old drip delivery completion, signed ingress, anonymous/OTP compatibility, lead enrollment/download creators, and private feedback SMTP/result writes. No test sends mail externally or starts a runtime.
