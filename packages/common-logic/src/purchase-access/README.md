# Purchase refund access

Al's September 7 rule is: confirmed successful refunds totaling the original one-time purchase/class payment end only that purchase's access; a partial refund keeps it. Monthly cancellation and retained drops are unchanged.

`PurchaseAccess` is a private, durable domain/user/course/membership/session record. An open record reserves native payment callback work across every await. Full-refund announcement atomically closes admission before capping the same access-period revision used by drip grants and delivery claims. Already admitted work drains before native status expires. Reads deny the ended session immediately, including Member Mimic, while another active purchase or later session can still grant access. Pending messages are cancelled; dispatching messages retain their actual result.

Only the app's original-payment proof adapter calls `endFullyRefundedPurchase`. It checks the original paid native invoice, current provider Checkout/payment/charge and complete refund history, never browser-supplied provider IDs. Partial, pending, failed and uncertain money alone create no end fact. A second paid invoice sharing a legacy session needs review. No publication/start dates or missing legacy payment mode are backfilled. A verified signed event can supply its independently checked mode without rewriting the receipt.

The first full-refund proof and native booking/payment history remain preserved. Class roster/tag entries lack per-grant provenance; ending content access therefore reports **Class roster needs review** while retaining potentially valid shared entries. Duplicate terminal reconciliation never re-runs class cleanup or alters a newer rejoin. A later bank return marks access recovery for review; enrollment is not recreated automatically.

A separate shared observation claim serializes native provider read/create/result/access work with every external purchase-access proof read, including partial/failed observations. A later known bank return cannot finish behind an older full observer and lose its recovery flag. The safe shared member/operator projection can show the persisted access outcome even before any webhook money ledger exists; money remains honestly unrecorded.

Reservations and observation claims have no time-based expiry. After an interrupted worker, retry the same refund once that worker completes. A genuinely crashed reservation remains pending for an operator: prove the exact worker cannot resume, retain the private record and process evidence, then use a reviewed exact-record comparison before removing only that reservation. Do not clear all writers or infer worker death from elapsed time. This increment adds no public maintenance endpoint or automatic recovery job.

Account erasure uses `deleteUserMemberAccess` after its existing account-write fence; course/tenant teardown uses the matching existing access cleanup helpers. They remove these access records without deleting original financial evidence. Late provider events do not recreate access records for an erased user. Deploying the source creates no records until normal activation or verified refund work occurs.
